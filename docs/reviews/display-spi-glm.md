## Findings

**Finding 1 — CONFIRMED (evidence conflict in the dispatch package; the thing nobody named).** The attached `enviro_dash.service` (sha256:35ce25662ddf2e28) carries `StartLimitIntervalSec=300` / `StartLimitBurst=5` under `[Unit]`. If those bytes were live and honored, the loop is bounded: with `RestartSec=30` and a start that never succeeds (counter never resets), the 6th start inside 300s is refused — ~5 restarts, then permanent failure. ~69k restarts since 2026-09-16 is impossible under that unit. `msg_enviro_dash_fix.md` ("StartLimitIntervalSec sits under [Service] → journal 'Unknown key … ignoring', effective StartLimitIntervalUSec=10s") and the dispatch premise ("Effective old startlimit10s with retry30s cannot bound this loop") are the accounts consistent with observed behavior; the attached artifact is not. Both cannot be the live installed unit. What breaks if unresolved: the provenance of the step-2 reconciliation and the "silent because ignored" diagnosis the start-limit fix answers — not the new bytes, which are sound under either account. Smallest proportional correction (one command, already inside plan step 3's declared preservation): before overwrite, record native `systemctl cat enviro_dash.service` and `systemctl show enviro_dash -p StartLimitIntervalUSec -p StartLimitBurst` as the deployed source of record, and state which account it matches; if it matches the attached artifact, re-examine the silence premise before accepting the 120s/1 rationale. Related one-liner: starting the replaced unit may need `systemctl reset-failed`, which clears the runtime counter only — not the journal history the plan says not to erase.

**Finding 2 — REFUTED (concern checked against source).** Claim considered: removing `Environment=PYTHONPATH=/home/pistrommy/projects` from the canonical unit breaks `shared` imports. Refuted: `enviro_dash3.py` performs `sys.path.insert(0, "/home/pistrommy/projects")` before `from shared.config_service import …`, and the deployed unit omits the variable too. No correction.

**Finding 3 — UNCONFIRMED (real, residual-shaped, not introduced here).** `OnFailure` alert delivery requires the stocks HTTP transport to be reachable at failure time; a failure ordered before network-online completes could fire `stocks_ops_alert@enviro_dash.service.service` with no network, and the supplied artifacts show no re-alert path for a failed alert oneshot (`alert_deadman`/`alert_state` are referenced but their sweep/heartbeat drivers are not attached, so coverage is unconfirmable from what I hold — a statement about evidence, not about the system). This is the pre-existing pattern shared with `enviro_backup.service` and is directed reuse (h); hardening it here would be the invented retry framework the dispatch excludes. Surfaced for operator residual adjudication; no correction within this change.

**Finding 4 — UNCONFIRMED (low; settles via the already-planned observation).** "One start per120s" states window semantics; the expected systemd 257 sequence — first exit, one refused restart at +30s, then failed state with no further automatic restart until manual reset or reboot (which is what makes the alert terminal and the containment real) — is not established from the supplied citations alone. Plan step 3 ("observe native rate limit" with the live GPIO failure) settles it; only the observed sequence should be recorded, not the assumed one. No artifact change.

Minor, immaterial, not a finding: the pi-config doc's "current04:15 host backup failed" vs the dispatch's failed04:09/replication-active04:10 reads as observation time vs event time.
